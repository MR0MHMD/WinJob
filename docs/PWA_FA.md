# راهنمای PWA وینجاب — مرحله اول

## مبنای کار و تحلیل پروژه

این patch روی شاخه `main` در commit زیر آماده شده است:

`4c9930133926c642dec670d79e5def42cb566eba`

بررسی با دسترسی فقط خواندنی گیت‌هاب انجام شد. تغییرات و commit بسته فقط در نسخه محلیِ کاری ساخته شده‌اند؛ هیچ push، pull request یا تغییری در ریپازیتوری آنلاین انجام نشده است.

WinJob یک برنامه Django با رندر سمت سرور است؛ برای نصب‌پذیری نیازی به تبدیل آن به React یا SPA نیست. وابستگی ثبت‌شده پروژه Django 6.0.8 است. قالب عمومی `templates/parent/base.html` و قالب مستقل مدیریت داخلی `templates/parent/support_base.html` محل اتصال PWA هستند. فرم‌های ورود و OTP، داشبوردهای کاربران، کمپین‌ها، کیف پول و صفحات پشتیبانی از این قالب‌ها استفاده می‌کنند. قالب Django admin و فاکتور چاپی رابط نصب دریافت نمی‌کنند.

در نسخه مبنا، لینک manifest در قالب عمومی مقدار `#` داشت و Service Worker وجود نداشت. آیکون نصب از تصویر موجود `static/finder/img/icons/favicon.ico` ساخته شده است؛ این فایل با وجود پسوند ico در واقع PNG است. چهار خروجی استاندارد PNG از همان نشان تهیه شده‌اند، از جمله آیکون maskable با حاشیه امن.

احراز هویت پروژه مبتنی بر session و شامل رمز و OTP است. ورود از `/accounts/login/` انجام می‌شود و مسیر `/accounts/dashboard/router/` کاربر را بر اساس نقش هدایت می‌کند. PWA حساب جداگانه‌ای نمی‌سازد؛ صفحه آغاز همان `/` است. بسته به مرورگر و سیستم‌عامل ممکن است در نسخه نصب‌شده نیاز به ورود دوباره داشته باشید.

پرداخت از مسیرهای `payment/` و `gateway/` استفاده می‌کند و بازگشت پرداخت به وضعیت session وابسته است. این مسیرها، مسیر خروج و Django admin از fetch handler کنار گذاشته شده‌اند. اعلان‌های موجود پروژه اعلان داخلی و تنظیمات بله هستند؛ این بسته Web Push اضافه نمی‌کند.

## امکانات تحویلی

- manifest واقعی، فارسی و راست‌به‌چپ؛ شناسه و محدوده ثابت `/`؛ اجرای `standalone`.
- آیکون‌های 192 و 512، آیکون maskable و Apple Touch Icon اندازه 180.
- ثبت Service Worker در ریشه با محدوده کل سایت و MIME صحیح.
- دکمه نصب وقتی مرورگر رویداد نصب را ارائه کند؛ راهنمای نصب دستی و راهنمای Safari.
- رابط نصب در پایین صفحات عمومی و پنل پشتیبانی؛ در حالت standalone مخفی می‌شود.
- پیام تشخیص قطع اتصال توسط مرورگر. این پیام تنها وضعیت `navigator.onLine` را نشان می‌دهد و تضمین نمی‌کند سرور در دسترس است.
- صفحه عمومی فارسی برای شکست ارتباط هنگام بازکردن صفحه؛ بدون وابستگی به CSS، فونت، API یا دیتابیس.
- کش نسخه‌دار و حذف فقط کش‌های قدیمی خود این قابلیت.
- اطلاع به‌روزرسانی بدون رفرش خودکار یا اجبار به فعال‌کردن نسخه جدید وسط فرم و پرداخت.

این مرحله، قابلیت ثبت سفارش، ورود، پرداخت، مشاهده اطلاعات شخصی یا همگام‌سازی عملیات در حالت آفلاین ایجاد نمی‌کند. هیچ صف درخواست آفلاین یا تکرار خودکار فرم وجود ندارد. سایت باید قبلاً آنلاین باز شده و نصب Service Worker موفق شده باشد تا صفحه قطع اتصال در دسترس باشد. اگر فضای ذخیره‌سازی مرورگر پاک شود، بازدید آنلاین دوباره لازم است.

## سیاست کش

| نوع درخواست | رفتار |
|---|---|
| یک صفحه عمومی `/offline/` | هنگام نصب، بدون ارسال credentials در Cache Storage ذخیره می‌شود |
| صفحه‌های GET هم‌دامنه | شبکه، با `cache: no-store`؛ فقط در شکست شبکه، صفحه عمومی قطع اتصال |
| HTTP 404 یا 500 | همان پاسخ واقعی سرور نمایش داده می‌شود |
| API، fetch معمولی، تصاویر و CSS/JS | Service Worker مداخله نمی‌کند؛ کش معمول HTTP تابع تنظیمات سرور است |
| POST و سایر متدها | Service Worker مداخله نمی‌کند |
| پرداخت، درگاه، خروج، Django admin | Service Worker مداخله نمی‌کند؛ در قطع اینترنت ممکن است خطای خود مرورگر نمایش داده شود |
| دامنه‌های دیگر | Service Worker مداخله نمی‌کند |

تنها سند عمومی قطع اتصال در Cache Storage نگهداری می‌شود. هیچ HTML شخصی، توکن، موجودی، فاکتور، پاسخ API یا فایل بارگذاری‌شده به این کش اضافه نمی‌شود. این سیاست جایگزین تنظیم صحیح هدرهای خصوصی در سرور، CDN یا سیاست تاریخچه مرورگر نیست.

## اعمال با git am در ویندوز / ترمینال PyCharm

1. فایل `WinJob-PWA-v1.patch` را دانلود کنید؛ مثلاً در پوشه Downloads قرار دهید. فایل شامل کد، آیکون‌های باینری، تست‌ها و همین راهنماست.
2. ترمینال را در ریشه پروژه، کنار `manage.py` باز کنید:

```powershell
git status
```

اگر تغییر ذخیره‌نشده یا فایل جدید متعلق به کار خودتان دارید، ابتدا آن‌ها را طبق روش معمول خود commit یا stash کنید؛ ادامه را با working tree تمیز انجام دهید. کد فعلی خودتان را با reset پاک نکنید.

3. یک شاخه مجزا بسازید و patch را اعمال کنید:

```powershell
git switch -c feature/pwa
git am --3way "$HOME/Downloads/WinJob-PWA-v1.patch"
```

مسیر فایل را با محل واقعی دانلود تطبیق دهید. در Git Bash هم همین الگوی مسیر HOME قابل استفاده است. `git am` خودش commit را می‌سازد؛ نیازی به اجرای جداگانه `git apply` یا کپی فایل‌ها نیست. دستور فوق هیچ push انجام نمی‌دهد.

اگر Git نام و ایمیل شما را تنظیم نکرده، مقادیر واقعی خودتان را در تنظیمات محلی همین ریپازیتوری وارد کنید و مجدداً اقدام کنید:

```powershell
git config user.name "Your Name"
git config user.email "your-email@example.com"
```

4. نتیجه را بررسی کنید:

```powershell
git log -1 --oneline
git show --stat --oneline HEAD
git status
```

مبنای دقیق patch همان commit ابتدای راهنماست. روی نسخه‌های دیگر، `--3way` در صورت موجودبودن اشیای مبنا امکان ادغام سه‌طرفه می‌دهد، اما نبود تعارض را تضمین نمی‌کند. اگر تعارض پیش آمد:

```powershell
git status
```

برای حل: فایل‌های متعارض را اصلاح کنید، فایل‌های حل‌شده را با `git add <path>` علامت بزنید و `git am --continue` را بزنید. اگر نمی‌خواهید ادامه دهید:

```powershell
git am --abort
```

این دستور عملیات نیمه‌تمام را لغو می‌کند. اگر patch کامل اعمال شده و بعداً خواستید کد آن را برگردانید، commit همین قابلیت را پیدا کنید و `git revert <commit-sha>` بزنید؛ برای worker نصب‌شده بخش بازگشت انتهای راهنما را هم بخوانید.

## راه‌اندازی و تست محلی

محیط مجازی معمول پروژه را فعال کنید. این patch پکیج تولیدی جدید و تغییر مدل دیتابیس ندارد؛ برای خود PWA migration لازم نیست. پیش‌نیازهای قبلی پروژه، دیتابیس و `.env` همچنان لازم‌اند؛ به‌ویژه تنظیمات فعلی بدون `BALE_BOT_TOKEN` بالا نمی‌آیند.

```powershell
python tests/test_pwa.py
node tests/test_pwa_worker.cjs
python manage.py check
python manage.py runserver
```

Node فقط برای تست منطق worker لازم است؛ سایت در زمان اجرا به Node نیاز ندارد. تست Python مستقل از دیتابیس و سرویس‌های خارجی است.

آدرس `http://127.0.0.1:8000` یا `http://localhost:8000` را باز کنید. Service Worker روی HTTPS یا localhost کار می‌کند. بازکردن `http://192.168.x.x:8000` از گوشی، معادل localhost نیست؛ برای تست گوشی از دامنه آزمایشی HTTPS استفاده کنید.

## استقرار روی سرور

```powershell
python manage.py check
python manage.py collectstatic --noinput
```

سپس سرویس Django را به روش معمول سرور خودتان restart کنید. فایل‌های `static/pwa/` باید مانند سایر staticها سرو شوند. مسیرهای زیر باید به Django برسند و با redirect ورود، صفحه HTML خطا یا مسیر static اشتباه جایگزین نشوند:

| URL | انتظار |
|---|---|
| `/manifest.webmanifest` | وضعیت 200، نوع `application/manifest+json` |
| `/service-worker.js` | وضعیت 200، JavaScript و `Service-Worker-Allowed: /` |
| `/offline/` | وضعیت 200، صفحه عمومی فارسی بدون اطلاعات کاربر |
| `/static/pwa/icons/icon-192.png` | PNG واقعی 192×192 |
| `/static/pwa/icons/icon-512.png` | PNG واقعی 512×512 |
| `/static/pwa/icons/maskable-512.png` | PNG واقعی 512×512 |
| `/static/pwa/icons/apple-touch-icon.png` | PNG واقعی 180×180 |

فرض این بسته نصب WinJob در ریشه دامنه است، نه زیرمسیر مثل `/winjob/`. دامنه در manifest هاردکد نشده؛ origin همان سایتی است که باز می‌کنید. برای production از یک دامنه اصلی ثابت با HTTPS معتبر استفاده کنید. CDN نباید `/service-worker.js` را طولانی‌مدت کش کند یا هدر no-store آن را حذف کند. اگر CSP سفارشی دارید، `worker-src 'self'`، دسترسی manifest و فایل‌های استاتیک را در سیاست موجود بررسی کنید؛ صفحه مستقل offline فعلاً CSS درون‌خطی دارد.

در تنظیمات commit مبنا، `DEBUG=True`، `ALLOWED_HOSTS=[]` و SECRET_KEY ثابت در کد دیده می‌شود. این موارد برای انتشار عمومی مناسب نیستند؛ اگر همین فایل را روی سرور استفاده می‌کنید، DEBUG را خاموش کنید، دامنه واقعی را در ALLOWED_HOSTS قرار دهید و کلید را با مقدار محرمانه جدید خارج از مخزن جایگزین کنید. تغییر کلید می‌تواند نشست‌های فعلی را نامعتبر کند. بسته حاضر تنظیمات تولید سرور شما را تغییر نمی‌دهد. تنظیم SSL/proxy را متناسب با زیرساخت واقعی انجام دهید.

## تست پذیرش روی مرورگر و گوشی

1. Chrome دسکتاپ: DevTools → Application → Manifest. نام، آیکون‌ها، start URL و نبود خطای manifest را بررسی کنید.
2. Application → Service Workers: worker ریشه باید activated باشد. یک بار صفحه را reload کنید تا کنترل شدن آن روشن باشد.
3. Cache Storage: فقط یک کش با پیشوند `winjob-pwa-offline-` و فقط `/offline/` داخل آن باشد. پس از دیدن داشبورد و کیف پول نیز نباید اطلاعات آن‌ها وارد این کش شود.
4. در پنجره عادی مرورگر، گزینه نصب را بررسی کنید. دکمه اختصاصی فقط زمانی نمایان می‌شود که مرورگر نصب را مجاز و رویداد مربوطه را ارسال کرده باشد. نصب‌بودن قبلی، مرورگر داخلی پیام‌رسان، حالت خصوصی و سیاست مرورگر می‌توانند مانع نمایش شوند.
5. نصب کنید؛ از آیکون سیستم اجرا کنید. نام و آیکون صحیح و پنجره مستقل را بررسی کنید. ورود با حساب فعلی، OTP و جابه‌جایی بین نقش‌های مجاز را آزمایش کنید.
6. روی یک صفحه عادی، Offline را فعال و صفحه دیگری باز کنید: باید صفحه فارسی قطع ارتباط دیده شود. اینترنت را وصل و «تلاش دوباره» را بزنید: همان آدرس قبلی باید از شبکه باز شود.
7. درخواست‌های فرم و API را با داده آزمایشی بررسی کنید؛ نباید پاسخ موفق ساختگی یا اطلاعات کاربر قبلی نمایش داده شود. API آفلاین عمداً fail می‌شود؛ مدیریت پیام خطا همچنان به کد فرم موجود وابسته است.
8. پرداخت sandbox را با اینترنت برقرار، رفتن به درگاه و بازگشت کامل تست کنید. روی دستگاه واقعی بررسی کنید بازگشت در همان محیط دارای session انجام شود. هرگز برای تست آفلاین پرداخت واقعی تکراری نفرستید؛ ابتدا وضعیت تراکنش را بررسی کنید.
9. از حساب اول خارج و با حساب دوم وارد شوید؛ داده‌های حساب اول نباید از کش PWA نمایش داده شوند.
10. iPhone/iPad: Safari → Share → Add to Home Screen؛ اجرای آیکون و ورود را جداگانه بررسی کنید. دکمه رویداد نصب Chromium در Safari معیار تست نیست.
11. به‌روزرسانی: محتوای صفحه offline را در محیط آزمایشی تغییر دهید و منتشر کنید. بعد از check update باید پیام نسخه جدید دیده شود، اما فرم باز نباید reload شود. تمام پنجره‌های مربوط به origin را ببندید، سپس باز کنید؛ کش نسخه قبلی خود PWA باید حذف شود.

## تست‌های بسته و محدودیت تأیید

تست Python، مسیرها، MIME، متدها، آیکون‌های واقعی، تغییر نسخه worker هنگام تغییر offline و عدم وابستگی سند offline به context کاربر را بررسی می‌کند. تست Node، سیاست fetch و کش، HTTP errorها، حذف محدود کش قدیمی، نصب ناموفق و استثناهای پرداخت را در محیط شبیه‌سازی worker بررسی می‌کند.

در محیط تهیه بسته، هر پنج تست Python و تست منطق worker با موفقیت اجرا شدند. وابستگی‌های همان requirements نصب شدند و `manage.py check` روی Django 6.0.8 بدون خطا بود. سه endpoint از URLconf واقعی پروژه با وضعیت 200 پاسخ دادند؛ کامپایل دو قالب پایه و کشف شش فایل استاتیک هم تأیید شد. برای عبور از الزام تنظیمات، فقط مقدار آزمایشیِ توکن در محیط تست قرار گرفت؛ هیچ سرویس بله، OTP یا پرداخت واقعی فراخوانی نشد.

این تست‌ها جای نصب واقعی Chrome/Safari، تست ورود و OTP روی سرور شما و پرداخت sandbox روی دستگاه واقعی را نمی‌گیرند. تلاش برای اجرای مرورگر خودکار در محیط تهیه بسته به علت ناموفق‌بودن دانلود Chromium کامل نشد؛ هیچ ادعای تست نصب واقعی گوشی برای این تحویل وجود ندارد.

## به‌روزرسانی و بازگشت

نسخه کش از محتوای worker و سند offline مشتق می‌شود. پس از تغییر هرکدام، نیازی به افزایش دستی شماره نیست. نسخه جدید منتظر بسته‌شدن تمام پنجره‌های تحت کنترل قبلی می‌ماند. `skipWaiting` و reload اجباری عمداً استفاده نشده‌اند تا فرم و پرداخت باز قطع نشود. کش فایل‌های JS/CSS معمول سایت تابع تنظیمات فعلی سرور است و این بسته آن را تغییر نمی‌دهد.

برای تست محلیِ حذف: DevTools → Application → Service Workers → Unregister؛ سپس فقط کش دارای پیشوند `winjob-pwa-offline-` را حذف کنید و صفحات را ببندید. پاک‌کردن تمام Site Data ممکن است کاربر را از حساب خارج کند.

برای بازگشت production، صرفاً حذف فایل worker از سرور، worker نصب‌شده روی دستگاه‌های قبلی را فوراً حذف نمی‌کند. ابتدا در همان URL `/service-worker.js` یک worker بازنشسته‌کننده منتشر کنید که کش‌های همین پیشوند را پاک و registration خود را unregister کند؛ آن را برای مدت کافی در دسترس دستگاه‌های قبلی نگه دارید. حذف registration فوراً سند باز را reload نمی‌کند و فعال‌شدن بازنشستگی هم به اتصال دوباره و چرخه مرورگر وابسته است. قبل از rollback گسترده روی staging تست کنید.

## مرحله بعد: TWA

پس از موفقیت تست PWA روی HTTPS و مشخص‌شدن دامنه نهایی، مرحله Android/TWA جداگانه انجام می‌شود. در آن مرحله شناسه بسته اندروید، امضا، ارتباط تأییدشده با دامنه و تست بازگشت درگاه تعیین می‌شود. این patch APK/AAB، تنظیمات انتشار فروشگاه یا Web Push ندارد.
