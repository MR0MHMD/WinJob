# ابزارهای جدید پنل وین دایرکت

این تغییر ادامهٔ پنل فعلی وین دایرکت است و وجود migrationهای `0001_initial` و `0002_alter_automation_options_and_more` و صفحات پنل قبلی را پیش‌فرض می‌گیرد.

## امکانات

- بخش کامنت هوشمند قبلی حفظ شده است.
- دایرکت: محرک دقیق/شامل، اولویت، پاسخ متنی، نمایش ویترین یا شروع فرم؛ اولین قانون فعال منطبق اجرا می‌شود.
- ویترین: ۱ تا ۱۰ کارت مرتب، عنوان و توضیح، تصویر HTTPS و یک دکمهٔ پیوند برای هر کارت.
- فرم: ۱ تا ۲۰ سؤال الزامی با انواع متن، عدد صحیح، ایمیل، همراه ایران و انتخاب از گزینه‌ها؛ تنظیم پیام پایان و کلمهٔ لغو.
- پاسخ‌نامه: مشاهدهٔ پاسخ‌های کامل، نیمه‌تمام و لغوشده، صفحهٔ جزئیات و خروجی واقعی XLSX با فیلتر وضعیت.
- شبیه‌ساز مکالمه با حفظ مخاطب، نمایش ۳۰ پیام آخر و گزارش جداگانهٔ پیام‌ها.
- ادمین فارسی، تاریخ شمسی، فیلتر و جست‌وجو؛ سوابق فقط قابل مشاهده‌اند.

تمام صفحات از `windirect/base.html` و در نهایت `parent/base.html` استفاده می‌کنند. فایل اصلی تم و زمینهٔ سایت حفظ شده‌اند. کلاس‌ها و استایل افزوده‌شده فقط در محدودهٔ پنل هستند.

## اعمال پچ

فایل `windirect-tools.patch` را کنار `manage.py` قرار دهید. این پچ افزایشی است؛ پچ‌های قبلی پنل باید قبلاً اعمال شده باشند.

```powershell
git apply --check windirect-tools.patch
git apply windirect-tools.patch
python manage.py migrate
python manage.py check
python manage.py test windirect
```

در استقرار با سرویس‌دهی فایل‌های استاتیک توسط وب‌سرور:

```powershell
python manage.py collectstatic --noinput
```

`openpyxl==3.1.5` از قبل در requirements پروژه هست. اگر محیط فعلی آن را ندارد، وابستگی‌های پروژه را نصب کنید. migration جدید فقط جدول‌های ابزارهای جدید را اضافه می‌کند؛ نیازی به حذف دیتابیس یا اجرای `--fake` نیست.

## آزمایش فرم از ابتدا تا اکسل

1. وارد `/windirect/panel/` شوید و یک حساب **آزمایشی** ثبت کنید.
2. در فرم‌ساز، فرمی برای همان حساب بسازید: سؤال اول «نام شما؟» از نوع متن و ترتیب ۱؛ سؤال دوم «شمارهٔ همراه؟» از نوع همراه ایران و ترتیب ۲.
3. در دایرکت هوشمند یک قانون با کلمهٔ «فرم»، تطبیق برابر، نوع پاسخ «شروع فرم» و فرم ساخته‌شده ثبت کنید.
4. در آزمایش دایرکت، حساب را انتخاب و شناسهٔ مخاطب را مثلاً `visitor-1` قرار دهید. پیام «فرم» را ارسال کنید.
5. در همان حساب و شناسه، نام و سپس شماره را در پیام‌های جدا وارد کنید. شمارهٔ نامعتبر نباید سؤال را جلو ببرد. در هر مرحله کلمهٔ لغو، فرم را لغو می‌کند.
6. به فرم‌ساز ← پاسخ‌ها و اکسل بروید. جزئیات پاسخ‌نامه و خروجی اکسل را بررسی کنید. صفر ابتدای شماره حفظ می‌شود.
7. برای آزمایش مخاطب جدید شناسه را عوض کنید. برای شروع فرم جدید پس از تکمیل یا لغو، کلمهٔ محرک را دوباره بفرستید.

## آزمایش ویترین

ویترین و کارت‌ها را برای همان حساب بسازید؛ یک قانون با کلمهٔ «محصولات» و پاسخ «نمایش ویترین» ایجاد کنید. در شبیه‌ساز، «محصولات» را بفرستید. پیوند تصویر باید عمومی و HTTPS باشد؛ سرور وینجاب تصویر را دانلود نمی‌کند. تصویر و دکمه در مرورگر نمایش داده می‌شوند.

## رفتارهای مهم

- حساب/ابزار کاربران دیگر در فرم‌ها و درخواست‌های دست‌کاری‌شده پذیرفته نمی‌شود. ابزار پاسخ باید متعلق به همان حساب قانون باشد.
- حساب ابزار پس از ساخت در پنل قابل انتقال نیست.
- در فرم فعال، پیام بعدی جواب سؤال جاری است، نه محرک قانون دیگر. کلمهٔ لغو استثناست.
- سؤال‌ها و تنظیمات هنگام شروع فرم نسخه‌برداری می‌شوند. ویرایش و حذف سؤال‌ها سابقهٔ قبلی را تغییر نمی‌دهد.
- غیرفعال‌سازی فرم شروع‌های جدید را متوقف می‌کند؛ فرم‌های شروع‌شده ادامه پیدا می‌کنند.
- شناسهٔ پیام تکراری همان خروجی قبلی را برمی‌گرداند و فرم را جلو نمی‌برد. استفادهٔ دوباره از شناسه با متن یا مخاطب متفاوت رد می‌شود.
- در اولویت برابر، قانون قدیمی‌تر زودتر بررسی می‌شود. ابزار پاسخ غیرفعال یا خالی از مسیر اجرا کنار گذاشته می‌شود.
- ابزار دارای قانون وابسته یا سابقه حذف نمی‌شود؛ از غیرفعال‌سازی استفاده کنید.
- خروجی اکسل همهٔ صفحات فیلتر فعلی را شامل می‌شود. ستون‌ها از نسخه‌های تاریخی سؤال‌ها ساخته می‌شوند؛ با تغییر عنوان/نوع سؤال ستون تاریخی جدا حفظ می‌شود. مقادیر متنی به فرمول Excel تبدیل نمی‌شوند.

## مرز این مرحله

این نسخه **بستر محلی و آزمایشی** است: اتصال OAuth متا، وب‌هوک، ارسال واقعی دایرکت، پنجرهٔ مجاز پیام‌رسانی، محدودیت نرخ، صف ارسال و مدل هوش مصنوعی هنوز پیاده‌سازی نشده‌اند. نمایش موفق در شبیه‌ساز به معنای ارسال به اینستاگرام نیست. پاسخ دایرکت فعلاً مبتنی بر قانون است.

سرویس `simulate_direct` عمداً فقط حساب آزمایشی را می‌پذیرد. برای نسخهٔ عملیاتی باید ورودی تأییدشدهٔ وب‌هوک، نگاشت مخاطب متا، بررسی مجوز ارسال، صف خروجی و سیاست تکرار ارسال جداگانه افزوده شوند. شناسه‌های مخاطب این مرحله نمونه هستند.

موتور آزمون از تراکنش و قفل حساب و محدودیت‌های یکتایی استفاده می‌کند. آزمون‌ها روی SQLite اجرا شده‌اند؛ رفتار هم‌زمانی زیر بار، ارسال واقعی متا و خروجی اکسل با حجم بسیار بزرگ در این مرحله آزموده نشده‌اند. برای داده‌های حجیم، خروجی باید به کار پس‌زمینه منتقل شود.
